# firewall

nftables, one table, default drop. `/etc/nftables.conf` is generated by the
script, so change the script (or `EXTRA_TCP_PORTS`) instead of editing the file,
or the next run will put it back.

## the ruleset

```nft
table inet filter {
    chain input {
        type filter hook input priority filter; policy drop;

        iif "lo" accept
        ct state established,related accept
        ct state invalid drop

        meta l4proto icmp accept
        meta l4proto ipv6-icmp accept

        tcp dport { 1, 22 } accept
    }
}
```

- `iif "lo"` so localhost keeps working.
- conntrack states first, otherwise replies to your own outbound traffic would
  be dropped and every `apt update` would hang.
- icmp is not a hole. ping and path mtu discovery are useful. `ipv6-icmp` is
  required for ipv6 to function at all.
- everything else inbound: dropped.
- output: accept. this box is a client, not a router.

extra ports:

```bash
EXTRA_TCP_PORTS="80 443"    # space or comma separated
EXTRA_UDP_PORTS="51820"
```

real ssh is always open on `SSH_PORT` (`1/tcp` by default). tcp/22 is also
allowed when the decoy module is selected or its deployed service is active.
skipping a module does not stop an existing service. cloudflare tunnels need
nothing (outbound only).

## docker, the annoying part

docker writes iptables rules into `table ip filter` and `table ip nat`. those
live next to this ruleset, not inside it. two consequences:

1. `flush ruleset` at reload time deletes docker's rules. containers lose
   connectivity until docker restarts. the firewall module restarts docker when
   it changed the ruleset, which re-adds them.
2. a forwarded packet still has to survive the `forward` chain in
   `table inet filter`. docker's own accept does not override a base-chain drop.
   that is why the forward chain accepts `docker0` and `br-*`.

published ports (`-p 8080:80`) are still reachable from outside even though the
input chain drops, because they are handled by nat/dnat and the forward chain.
if you want a published port to be private, bind it to `127.0.0.1` and put a
tunnel or proxy in front. the host firewall is not a substitute for docker's
port mapping.

## fail2ban lives here too

fail2ban's nftables action creates its own table (`f2b-table`) and drops banned
addresses from there. multiple base chains on the same hook are evaluated
independently; a drop in one is enough. that is why a fail2ban ban works even
though its rules are not in `/etc/nftables.conf`.

reloading this ruleset flushes that table. the module restarts fail2ban after,
so bans come back.

## adding ports

1. prefer the config: `EXTRA_TCP_PORTS="443"`
2. `sudo bash debian13-postinstall.sh --only firewall`
3. or live, without touching the file:

```bash
sudo nft add rule inet filter input tcp dport 443 accept
```

live rules vanish on the next reload. the file is the source of truth.

## debugging

```bash
sudo nft list ruleset
sudo nft list chain inet filter input
sudo nft -c -f /etc/nftables.conf     # validate without applying
sudo nft monitor trace                # noisy but honest
sudo journalctl -u nftables --since -10min
```

counters are the fast way to see if a rule matches:

```bash
sudo nft -a list chain inet filter input
```

a listener that is up but unreachable is almost always: wrong chain, wrong
family (`inet` vs `ip`), or the provider's own firewall in front.

## cloudflare

tunnels dial out from the box. no inbound port, no dns
record pointing at the vps, no certificate to renew. if you add a tunnel and
also open 443 "for safety", you reopened the thing the tunnel was avoiding.
